# e2e-report

Consolidate a task's latest results and export a machine-readable summary.

Shared conventions: `../_shared/conventions.md`.

**Input:** `<slug>`, with `reports/<slug>/report.json` present. If it is missing, run `/e2e run` first.

**Output:** the analysis you add to `reports/<slug>/report.md` — **written in Vietnamese** (see the language policy in conventions).

`report.csv` is **generated by the engine**, not written here. Every run emits it alongside `report.md` with the columns `TC ID, Phase, Target, Risk, Status, Scenario, Detail, Type`. Do not hand-write or reformat it: a mechanical projection of the run belongs in code, where it stays deterministic and costs nothing.

## The report is for the tester, not a work log

The reader wants two things: **which bugs exist**, and **which cases passed, failed or were not verified**. Write only that. The engine already produced the skeleton with numbered sections — fill section 1 and leave the rest as generated.

**Do not add sections about your own process.** These are noise and must not appear: what you automated during this run, how many records you created through the API, incidents while re-running, spec bugs you fixed along the way, state pollution you cleaned up, or which cases remain un-automated. That information belongs elsewhere — coverage and automatability in `plan.md`, data preparation in `data.md`, chains in `project-notes.md`.

If a run-time incident changes what the results *mean* — for example leftover state made a case fail — say it in one line inside the affected bug or case entry, not as its own section.

## Steps

1. Read `reports/<slug>/report.json`, plus the existing `report.md` when it already carries content.

2. **Fill section 1 — Bug.** One block per bug, using the template the engine left in place. Cover both **newly appeared bugs** and **previously reported bugs re-verified in this run** (fixed, or still reproducing). Every block needs:
   - **Hiện tượng** — what was actually observed, quoting the value or text seen.
   - **Kỳ vọng** — what the acceptance criterion requires, citing the AC.
   - **Tái hiện** — numbered steps precise enough that the tester can reproduce it **by hand** without reading the spec: which account, which page, which action, in order.
   - **Bằng chứng** — the screenshot in `artifacts/` and the trace when one exists.
   - **Nghi ngờ nguyên nhân** — `file:line`, when the code makes it clear.
   - **Trạng thái** — new, fixed and verified, or still reproducing.

   Do not report a failure as a bug until its category is settled: `[NEEDS-SELECTOR-REVIEW]` and flaky failures are spec or environment problems (see `../_shared/references/flaky-taxonomy.md`), and claiming an environment fault requires a verification you quote.

3. Leave the generated sections **2. Kết quả theo case**, **3. Case chưa kiểm được** and **4. Console đáng chú ý** as they are. Add the link to `html/index.html` beneath the table.

4. The only CSV column the engine leaves blank is **`Type`** (`feature`, `spec`, `flaky`) — a judgement the runner cannot infer. Fill it from your classification when the team needs it.

5. Summarise in chat, briefly: bug count split into new versus re-verified, pass / fail / not-verified totals, and which items need a developer versus a spec fix.
